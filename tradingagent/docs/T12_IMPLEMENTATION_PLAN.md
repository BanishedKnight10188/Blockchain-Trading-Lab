# T12反馈与成交归属实施计划

沿用已验证SQLite Journal/CAS/账户导入和T11发布事实，不重写、不新增交易所写能力。
全部反馈和归属操作是本地事实记录，不下单，不把用户想法当作交易所成交。

接口预检：T11不可变DecisionCompletion与T12可变建议状态分别读取；查询须核验
当前CAS投影，不能根据历史completion重新显示行动。T06导入提供UNCLASSIFIED
归属revision1，T12明确分类从revision2追加，不能另建一个初始归属事实。
规则：反馈操作保留自己的scope/幂等标记；成交归属只按完整交易身份关联。

## 第一段：反馈事实与权威校验

- 新增FeedbackStorePort，FeedbackService.record使用已有DecisionFeedback/FeedbackReceipt。
  独立想法保持human；采纳/拒绝/修改关联原建议，original_author永远agent。
- 当前采纳须同时检查已发布且未终结的建议、原会话/风格/账户scope与版本、当前行情/
  账户/硬纪律。服务预检后，存储写锁内再核验时效和权威状态，防止读取与提交间竞争。
  缺失/过期/已取代建议不被采纳为当前建议；不将记录反馈解释成真实执行授权。
- 拒绝/修改不依赖当前行情或硬风险可采纳性；仍校验scope/provenance/未响应的CAS。
  过期建议的拒绝保留人类事实，建议投影转EXPIRED；已接受/拒绝不能反转。
- 反馈ID与内容冻结；精确重试返回第一次回执，不重新改变建议或审计。不同输入同ID拒绝。
  Feedback事实及建议状态变更同事务；event-only伪提交、写入失败、旧版本竞争须回滚。
- 保持DecisionCompletion/原始Recommendation不变；可变建议状态保存在已有CAS投影。
  查询读取当前投影，不把已采纳/拒绝的历史completion再显示为当前行动。

## 第二段：真实成交关联与追加纠正

- 只能关联已导入且scope完整的Binance Spot BTCUSDT成交，身份按账号/市场/品种/trade_id，
  不按时间自动猜测。首次导入保留UNCLASSIFIED；明确确认后才分类。
- 原建议者、最终决策者human、执行者human分别保存；关联建议必须存在且同scope，
  不能篡改原建议作者。CAS追加纠正保留旧归属版本；精确重试不得产生新纠正。
- paper/真实账号命名空间隔离，越scope/不存在成交拒绝。对不完整历史不构造0成本或盈亏。

## 第三段：手工报告与Web装配

- 手工报告使用独立USER_REPORTED模型，记录用户报告的执行时间与来源；有明确exchange
  trade_id才尝试核实，scope/数量/方向/价格等矛盾标冲突。没有ID保持待核实，不冒充成交。
  核实追加关联事实，保留原手工报告；不合并相近时间或相同金额的不同成交。
- 本地Web反馈/归属接口沿用cookie/Origin/CSRF与严格输入/版本，API投影不导出账户敏感标识。
  Fake→SQLite→Web覆盖建议→反馈→导入成交→明确归属→追加纠正。完整页面在T14继续。

先观察目标缺失RED，再实现、狭窄验证、独立复核与最终回归。正式Conda解释器，
不安装依赖，不读取真实凭据，不发收费请求。每段通过后更新台账，未验证部分保持待办。
